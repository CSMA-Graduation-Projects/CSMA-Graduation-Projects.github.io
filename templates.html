# 入组与阶段计划模板

用途：用于本科科研训练、毕业设计或硕士入学后的首次对齐，明确本阶段做什么、用什么资源、何时提交什么材料。它是工作计划，不能替代学校注册、选导师、培养计划等正式手续。

填写说明：将方括号替换为实际内容；未知项写“待核实＋责任人＋核实日期”，不要留给读者猜测。正式培养要求以学校、学院当年文件为准，先填写依据，再约定研究任务。示例仅说明填写粒度，不代表必须完成的任务量。

## 一、基本信息与适用依据

| 必填项 | 填写内容 |
| --- | --- |
| 姓名或项目代号、培养类别 | ［本科科研训练／本科毕业设计／学术硕士／专业硕士等］ |
| 当前阶段、计划覆盖时间 | ［起止日期；本阶段结束时应达到的状态］ |
| 指导与协作人员 | ［指导人员、日常对接人、需协作事项］ |
| 培养依据 | ［文件名称、发布单位、年份、链接或相对路径；待核实项］ |
| 当前基础 | ［已学课程、可运行项目、阅读基础；附可核验材料］ |
| 时间与资源约束 | ［课程安排、设备权限、数据授权、预计不可用时段］ |

## 二、目标与任务拆分

阶段目标写成可观察的结果，例如“在授权样本上完成基线复现，记录失败原因”，不写“提升科研能力”。每项任务最多对应一个主要交付物。

| 任务 | 输入与前置条件 | 具体交付物及位置 | 完成判据 | 责任人／日期 |
| --- | --- | --- | --- | --- |
| ［任务一］ | ［资料、权限、设备］ | ［报告、代码、运行记录］ | ［他人如何判断完成］ | ［填写］ |
| ［任务二］ | ［填写］ | ［填写］ | ［填写］ | ［填写］ |

## 三、协作与风险约定

- 沟通：［例会周期、正式请假或审批渠道、紧急联系渠道；按实际制度填写］。
- 任务记录：［使用的项目空间、版本管理方式、提交命名；不得写入账号密码］。
- 数据与伦理：［数据来源、允许用途、是否涉及个人信息、需先完成的授权或伦理程序］。
- AI 辅助：［允许用途、需记录或披露的范围；关联 AI 使用记录］。
- 主要风险：［风险、触发信号、备用任务、需要谁协助；如算力不可用先完成小规模核验］。
- 变更方法：目标、数据、人员或时间变化时，说明原因、影响及新计划，保留旧版。

## 四、检查与验收

- [ ] 每项任务都有输入、交付物、时间和可观察的完成判据。
- [ ] 校级手续与研究任务分别列明；没有把待核实要求写成已确认规定。
- [ ] 已确认必要的数据权限与资源；尚未获批的任务不会提前执行。
- [ ] 已约定遇到阻碍的报告方式及下一次检查时间。

审核记录：［审核人／日期／通过、补充后通过或退回／需要补充的内容］。学生确认：［已理解的任务与仍有疑问之处］。只有实际确认后才填写“已确认”。

# 科研训练任务卡模板

用途：把本科科研训练或硕士研究中的一个阶段目标拆成可开始、可提交、可验收的小任务。适合初次阅读、复现、数据核查、原型实现或问题验证，不以“熟悉某领域”作为唯一任务。

填写说明：一张卡只处理一个主要问题。目标应与学生基础、课程安排和资源匹配；先明确最小交付，再列可选扩展。示例“在授权小样本上跑通基线并解释一个失败案例”比“学习大模型”更可验收。

## 一、任务定义

| 必填项 | 填写内容 |
| --- | --- |
| 任务编号、负责人、日期 | ［唯一编号、开始与检查日期］ |
| 培养阶段与任务来源 | ［本科科研训练／毕业设计／硕士；关联阶段计划］ |
| 要回答的具体问题 | ［为什么做、结果用于哪个后续决策］ |
| 当前基础与前置材料 | ［必要概念、指定论文、已有代码；阅读或运行状态］ |
| 最小完成目标 | ［可检查的结果；例如能复述机制并提交运行记录］ |
| 不在本次范围的内容 | ［本次不扩展的数据、算法、系统或额外功能］ |

## 二、步骤与交付

| 步骤 | 要做的事 | 产出与证据位置 | 自查方法 | 截止日期 |
| --- | --- | --- | --- | --- |
| 理解问题 | ［阅读并解释输入、输出、假设］ | ［短说明、图示或阅读笔记］ | ［能否用一个具体例子解释］ | ［填写］ |
| 最小尝试 | ［使用许可范围内的样本或环境］ | ［代码、配置、实际日志］ | ［他人能否重复关键步骤］ | ［填写］ |
| 解释结果 | ［核对输出与一个失败案例］ | ［观察、疑问、后续建议］ | ［结论是否超出证据］ | ［填写］ |

可选扩展：［只有最小目标验收后再做的内容；不把扩展默认为必做］。

## 三、资源、阻碍与求助

- 必要资源：［数据许可、软件、设备权限、预计运行成本；不得记录密钥］。
- 风险与伦理：［是否涉及个人数据、外部服务、未公开资料；前置审批］。
- 遇到阻碍时：记录［复现步骤、错误信息、已尝试办法、最小示例］后提出具体问题。
- 检查节点：［何时提交什么供讨论；无法按时完成时何时说明影响］。
- 证据说明：真实运行、作者结果、保存记录回放和人工样例分别标注；未运行不能填“已复现”。

## 四、验收与下一步

- [ ] 必交材料均有可访问的位置，文件和描述相符。
- [ ] 学生能解释关键过程、结果与局限，而非仅展示截图。
- [ ] 成功和失败均据实记录，引用、授权及 AI 辅助情况清楚。
- [ ] 后续建议基于本次发现，任务没有无限扩展。

验收结果：［通过／补充后复核／调整任务；说明具体原因］。

反馈与行动：［审核人、日期、需要修改的内容、责任人、复核日期］。

学习反思：［本次掌握了什么；仍不理解什么；下一张任务卡解决什么］。

# 选题论证与范围界定模板

用途：用于本科毕业设计、科研训练或硕士选题的比较和决策。重点回答问题是否真实、已有方法哪里不足、当前资源能否完成，而非先给题目堆砌技术名词。最终选题须按学院程序确认。

填写说明：先记录证据，再提出判断；“预计有效”属于假设，不能写成结果。每个候选题至少说明一个可能导致放弃的条件。创新要求和成果形式引用本培养类别的正式依据，不自行设定统一标准。

## 一、选题信息

| 必填项 | 填写内容 |
| --- | --- |
| 项目代号、拟题、版本日期 | ［题目应体现对象、问题或目标，避免范围过宽］ |
| 培养类别与时间窗口 | ［科研训练／毕业设计／学术或专业硕士；可投入周期］ |
| 选题来源与适用要求 | ［实际场景、前期项目或文献；学院文件名称与链接］ |
| 一句话研究问题 | ［在何种场景下，什么对象存在什么可验证的问题］ |
| 预期使用者与价值 | ［谁会使用结果；若问题解决，具体改变什么］ |

## 二、问题依据与候选方案

| 证据或候选方向 | 已知事实与来源 | 尚不确定的判断 | 下一步验证 |
| --- | --- | --- | --- |
| ［实际案例／论文／需求记录］ | ［链接、时间、样本范围］ | ［是否具有代表性］ | ［如何收集反例］ |
| ［候选题甲］ | ［现有方案及主要不足］ | ［核心假设］ | ［最小实验及周期］ |
| ［候选题乙］ | ［同上］ | ［同上］ | ［同上］ |

区分真实场景证据、公开数据结果、人工构造示例和待验证推测。受控示例只能说明机制，不直接证明普遍需求。

## 三、拟采用题目的边界

- 研究对象与输入输出：［明确任务单位、使用环境、输入条件、产出形式］。
- 核心问题：［列一至三个可回答的问题，并说明对应观察指标］。
- 纳入范围：［数据、场景、方法、版本与适用条件］。
- 排除范围：［本阶段不研究哪些情况，并说明原因］。
- 基线与评价：［与什么比较；指标定义、比较公平性及失败案例如何记录］。
- 预期贡献：［方法、系统、数据或经验结论；说明与现有工作的差异证据］。
- 可行性：［数据许可、设备、技能、协作支持和最小验证结果；未执行写待执行］。
- 风险与退出条件：［如数据无法合法获取、基线已足够、预期增益无法观察时如何缩小或换题］。

## 四、决策与验收

选择理由：［为什么选此题、放弃其他候选；不能仅写“感兴趣”］。

- [ ] 问题由可追溯证据支撑，假设与已知结论分开。
- [ ] 题目范围与时间、资源、培养要求匹配。
- [ ] 数据授权和可能需要的伦理审批已列入前置条件。
- [ ] 最小验证有明确交付物、期限和停止条件。

评审意见：［确认／修改范围／暂缓；理由、责任人、复核日期］。确认记录：［实际审核人及日期］。

# 本科毕业设计任务书工作底稿

用途：协助学生与指导人员在正式下达任务书前明确题目、任务、技术要求、进度和提交材料。它是工作底稿，学校或学院正式任务书优先，不能代替签字、审核与系统下达。

填写说明：围绕专业培养目标和可完成的工作安排任务，不把硕士论文或团队全部工作直接下放给本科生。研究类、设计类和工程实现类可采用不同成果形式，但都应有可核验的个人工作和评价依据。

## 一、基本信息与正式要求

| 必填项 | 填写内容 |
| --- | --- |
| 学生或项目代号、专业与年级 | ［必要信息；共享版本不放学号等非必要个人信息］ |
| 题目、类型与题目来源 | ［研究／设计／工程等；项目或实际问题来源］ |
| 指导人员与协作边界 | ［指导关系、团队共享部分和个人独立任务］ |
| 正式模板与制度依据 | ［学校、学院、年份、文件版本及链接］ |
| 起止日期与正式节点 | ［选题、开题、中期、论文、答辩等当年安排］ |

## 二、任务与技术要求

问题背景：［服务什么对象、解决什么问题、已有条件与需要完成的部分］。

| 任务编号 | 具体工作内容 | 输入与资源 | 必交成果 | 完成判据 |
| --- | --- | --- | --- | --- |
| ［T01］ | ［例如分析需求并界定系统范围］ | ［资料、样本、许可］ | ［需求说明及确认记录］ | ［关键场景和异常规则明确］ |
| ［T02］ | ［方法设计、实现或研究验证］ | ［环境、数据与技能］ | ［设计、代码、实际记录］ | ［与目标对应的可观察结果］ |
| ［T03］ | ［论文撰写与材料整理］ | ［真实工作证据］ | ［论文、报告、归档清单］ | ［引用、结果和版本可核验］ |

技术约束：［平台、接口、指标、测试条件、授权范围及依据］。不在范围内的任务：［明确排除，避免不断追加功能］。

个人贡献：［与已有代码、合作同学或第三方工具的边界，如何记录本人完成部分］。

## 三、进度与指导安排

| 阶段与日期 | 阶段交付物 | 检查方式 | 受阻时的调整办法 |
| --- | --- | --- | --- |
| ［开题准备］ | ［综述、方案与计划］ | ［讨论或正式评审］ | ［填写］ |
| ［中期检查］ | ［已实现内容和实际验证］ | ［材料、演示和证据核查］ | ［填写］ |
| ［完成与答辩］ | ［论文、测试、修改与归档］ | ［按学院流程验收］ | ［填写］ |

基础资料与参考文献：［可访问的入门材料和关键来源；说明用途，不只堆积条目］。

## 四、自检与正式下达

- [ ] 工作量与学生基础、资源和学期节点匹配。
- [ ] 任务、成果与验收条件对应，个人贡献可解释。
- [ ] 数据授权、引用、AI 辅助和学术规范要求明确。
- [ ] 实际运行与示例或回放分开记录，失败和限制允许如实报告。
- [ ] 已按学校正式模板转换并完成要求的审核、签字或系统手续。

底稿确认：［学生、指导人员、日期、需要调整内容］。正式任务书状态：［待下达／已下达；正式文件位置和日期］。任务变更须保留原稿并按适用程序确认。

# 文献综述与证据矩阵模板

用途：为选题、开题及论文相关工作建立可复查的文献证据，形成有比较、有局限、有研究问题的综述。矩阵是分析工具，不能用论文数量代替综述质量。

填写说明：先写检索边界，再筛选、阅读和归纳。检索日期与版本必须保留；数据库更新后应记录增补过程。没有阅读全文的条目标明“仅摘要”，不要据此断言方法细节或实验结论。引用格式与综述篇幅遵从学校正式要求。

## 一、综述范围与检索方案

| 必填项 | 填写内容 |
| --- | --- |
| 综述问题与应用背景 | ［希望解释的技术发展、方法差异或证据缺口］ |
| 时间、语言与主题边界 | ［范围及理由；不随意排除不支持预期的研究］ |
| 检索来源与日期 | ［数据库、会议期刊官网、预印本平台；最后检索日期］ |
| 完整检索式 | ［保留关键词、逻辑关系、过滤条件，能够重复检索］ |
| 纳入与排除标准 | ［研究对象、任务、证据类型；排除理由可复核］ |
| 筛选记录位置 | ［候选文献表、去重依据、每项排除理由的相对链接］ |

## 二、文献证据矩阵

填写说明：先确认本人适用的形式、时间、地点、审批和考核要求，再开展依赖批准的工作。实践安排、指导关系与成果使用应有明确依据；不在此设置统一实践时长或成果数量。

| --- | --- |

| 实践单位、地点与形式 | ［集中、分段或校内外安排；以实际认可范围为准］ |
| 起止日期与时间安排 | ［课程、研究及安全安排的衔接］ |
| 校内与实践指导人员 | ［职责、检查方式及联系渠道；仅保留必要信息］ |
| 申请、协议与安全手续 | ［审批、保险或安全培训等适用项目；材料位置与状态］ |
| 数据和知识产权约定 | ［保密、成果使用、论文引用、代码与数据可带回范围］ |

- 评价与认定：［单位或实践指导评价、校内审核、正式成绩或认定依据］。

填写说明：会前填写议题和材料，会中记录决定及理由，会后确认责任人与期限。区分“建议”“已达成决定”和“待审批”；未经确认的判断不要写成导师或团队承诺。参会与请假遵循实际制度，不设置统一在线时长。

# 课题、计划与资源变更记录模板

填写说明：先保存原计划，再说明为什么改变、替代方案是什么、会影响哪些交付物。提出变更不代表已获批准；记录中应区分草案、已讨论、已确认和正式审批完成。

## 三、校验与恢复核对

- 校验范围：明确［校验清单自身及临时文件等排除项］；复制或解压后重新校验并保存结果。
- 可用性：在干净目录按 README 检查入口，记录［实际执行步骤、环境、结果］。只检查文件存在时写“结构检查”，不能写“完整复现”。
- 数据边界：原始数据和处理数据分别标识；需授权的数据验证访问规则，不擅自复制公开。
- 备份恢复：记录［备份版本、负责人、恢复演练抽检材料、校验结果］。

# 阶段移交与离组交接模板

用途：在项目换人、学生毕业、设备交还或协作结束时交接研究材料、系统和待办，保证接管者知道当前状态和可继续工作的入口。离校手续与资产处置仍按学校制度办理。

填写说明：交接对象以必要范围为限，不把个人账号、密码或无关个人材料转交他人。交付人先整理清单和操作说明，接管人实际抽检后确认；发送一个压缩包不等于交接完成。

| --- | --- |

| 交付人、接管人及确认人员 | ［按实际职责填写］ |
| 交接范围与边界 | ［本次移交什么；哪些仍由原责任人处理］ |

| 归档版本 | ［归档清单、README、校验文件的位置］ |

## 四、交接验收

- [ ] 文件清单、版本、校验结果和权限说明齐全。
- [ ] 接管人已从入口实际找到材料，并抽检关键运行或恢复步骤。
- [ ] 原始数据、未公开论文、匿名版本及第三方资料按授权保存。
- [ ] 待办、故障、未核实结论与后续责任明确。
- [ ] 资产、平台权限及正式离组手续分别有完成依据。

确认记录：［双方姓名或项目代号、日期、实际验收范围、保留问题］。

未完成项处理：［责任人、补交日期、复核方法］。未经接管确认的项目保持“待接收”，不要写为已完成。

没有匹配的模板

试试“论文”“实验”“归档”等关键词，或清空筛选。

填写与提交前

删除指导性示例，不能核实的事项写“待核实”，不适用项注明原因。填写后的评审意见、个人信息、未公开结果和受限数据不上传公共站点。模板没有签字、审核或学位资格认定效力。
