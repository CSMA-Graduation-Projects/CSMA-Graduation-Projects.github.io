01

文献调研与综述

从“读过若干论文”走到能比较问题、方法、证据和局限。

返回选择 ↑

初学者最小组合Zotero + Excel + VS Code

按这几步推进

  1. 先写研究问题、检索词、数据库、检索日期和纳入排除条件；用 Zotero 按主题收集条目，逐篇核对元数据与原文。
  2. 给每篇核心文献写结构化阅读记录：问题、对象、方法、数据、评价、发现、局限；关键判断标明原文页码或章节。
  3. 在 Excel 或 CSV 中建立综述矩阵，一行一篇文献；列出任务、数据规模、基线、指标、可复现材料、证据强弱和与本课题的关系。
  4. 按“已知什么—证据有什么限制—还需验证什么”组织综述；写入 Word 时使用 Zotero 引文插件，LaTeX 路线导出 BibTeX / BibLaTeX 并检查引用键。

交付什么

  • literature-matrix.xlsx 或 .csv：至少含来源标识、问题、方法、证据、局限。
  • reading-notes.md、search-log.md；按需导出的 references.bib / .ris 和综述正文。

怎样确认完成

  • 抽查每项重要结论，能回到原论文具体位置；区分作者报告与自己的判断。
  • 矩阵能解释不同研究为何可比或不可比；不是摘要粘贴集合。
  • 新增一条引用后，正文与参考文献能一致更新；附件权限符合来源要求。
需要换工具或增加工具时
  • 只需简单矩阵时用 CSV + VS Code；阅读笔记已有固定习惯时可继续用 Obsidian 或 OneNote。
  • 优先掌握 Zotero 原生导出与 Word 插件；需要自动维护 LaTeX 引用键时再评估第三方扩展，不将其视为必需。

容易误用的地方

  • 导入 PDF 不等于已核对文献；AI 生成的作者、DOI 或结论必须回原文验证。
  • Markdown 适合记录与交换文字，不能把 .md 改后缀当作符合学校格式的 Word 文件。
论文阅读与复现判断 ↗文献综述与证据矩阵 ↗选题论证与范围界定 ↗

功能依据 Zotero：入门、条目与笔记 · Zotero：Word 插件与引用更新 · Zotero：书目与 BibTeX / RIS 导出

02

实证复现、算法实验与数据分析

让每张表、每条结论都有对应的输入、版本、运行记录和计算过程。

返回选择 ↑

初学者最小组合VS Code + Git + Python + venv

按这几步推进

  1. 先确定复现对象、数据许可、指标、基线与可接受差异；记录作者报告值，保留数据原件和获取说明。
  2. 选择独立 Python 环境并在 VS Code 确认解释器；记录系统、Python、依赖、硬件、随机种子和完整命令。先跑小样例，再扩大规模。
  3. 把清洗、划分、运行、评价与绘图写成明确步骤；为每次运行分配编号，保存配置、输入标识、退出状态、完整日志和原始输出。
  4. 用脚本从保存的原始输出重算指标，报告重复运行差异、失败案例与限制；算法对比同时固定输入规模、资源条件与计时范围。
  5. 在新的输出目录按 README 重跑一个最小实验；核对结论能否由该记录支持，不能把离线重算写成新一轮真实运行。

交付什么

  • README.md、requirements.txt 或项目锁定文件、脚本、Git 提交号和环境记录。
  • run-manifest.json、config.json、完整日志、原始结果 .jsonl / .csv、分析脚本与图表 .svg / .pdf。

怎样确认完成

  • 另一位同学能按命令定位输入并复跑最小样例；失败也有退出码与记录。
  • 论文表格能从保存的原始结果计算得到，手工修改有明确追踪。
  • 检查数据泄漏、划分重叠、评价口径、异常处理与统计方法是否适合研究问题。
需要换工具或增加工具时
  • 小规模初查可用 Excel；用于论文的重复计算应保留公式和参数，复杂或批量统计转为脚本。
  • 只有论文明确依赖容器、特殊硬件或操作系统时再准备对应环境；Notebook 用于探索时，交付前清空输出并按顺序重跑。
  • 学习统计方法先理解假设与适用条件，再选择 SciPy 或其它库，避免因某个按钮可用就直接套用检验。

容易误用的地方

  • pip freeze 只反映部分 Python 依赖信息，不等于系统、GPU、驱动、数据和模型环境已完整记录。
  • 截图、进度条、安装成功和一个示例通过，都不能代替完整实验结果。
实验、复现与运行证据 ↗科研训练任务卡 ↗

功能依据 VS Code：Python 环境、调试与测试 · Python：独立虚拟环境与重建 · Git：记录变更与检查差异 · Excel：分析工具库

03

软件原型开发与测试

从可演示功能走到输入、行为和边界都能验证的可交付系统。

返回选择 ↑

初学者最小组合VS Code + Git + draw.io

按这几步推进

  1. 把需求拆成用户任务、输入输出、约束和验收条件；用 draw.io 画数据流、模块关系及关键异常分支。
  2. 按最小可运行功能建立项目，明确依赖与启动方法；每次提交只处理可说明的变更，提交前查看差异。
  3. 按项目技术栈运行测试：Python 项目可用 unittest / pytest，前端项目使用项目已有工具；覆盖正常、边界、失败与权限场景。
  4. 将测试结果、演示步骤和已知限制关联到当前版本；修复问题后重跑受影响检查，再完成一次端到端演示。

交付什么

  • 需求与设计说明、可编辑 .drawio 源文件及 .svg / .pdf 导出。
  • 代码、依赖声明、启动命令、测试用例与实际运行结果、演示输入和交付 README。

怎样确认完成

  • 按清洁环境说明启动，关键用户路径可独立完成，失败情况有清楚反馈。
  • 测试断言检查用户可观察的行为；记录实际运行日期、版本和结果。
  • 提交包不含密钥、个人数据、临时缓存与无关的大文件；第三方许可已核对。
需要换工具或增加工具时
  • 已有成熟技术栈时优先沿用，Python 并非所有软件项目的必选语言；Node/npm 等按项目需要使用。
  • EdrawMax 可作熟悉的绘图替代，但交付时同时保存原始工程与通用 PDF / SVG，并检查接收方能打开。

容易误用的地方

  • AI 生成了测试代码不等于测试已通过；页面能打开也不等于流程完整。
  • 流程图应画出关键判断与回退；不要只堆软件图标或用截图代替可编辑设计。
需求、详细设计与测试报告 ↗实验、复现与运行证据 ↗阶段移交与离组交接 ↗

功能依据 VS Code：Python 环境、调试与测试 · Git：记录变更与检查差异 · draw.io：源文件与 SVG / PDF 导出

04

LLM、Agent 与 RAG 研究

先验证任务与评价是否成立，再控制模型、数据、工具和费用开展实验。

返回选择 ↑

初学者最小组合VS Code + Git + Python + venv

按这几步推进

  1. 写清任务、数据范围、基线、成功与失败定义，区分模型回答质量、检索质量与端到端完成率；先建立可人工核对的小样本。
  2. 使用已获授权的模型或服务，记录模型标识、版本或访问日期、提示词、参数、数据快照、工具配置和预算；先做少量真实调用验证。
  3. RAG 先保存文档来源、切分规则、检索候选与引用位置，再评估回答；Agent 记录每步输入、工具调用、返回值、终止原因和实际环境状态。
  4. 分别保存真实模型运行、离线回放、手工构造样例和失败记录；评测脚本检查原始轨迹，不能只看模型自评“已完成”。
  5. 检查数据隔离、基线公平性、重复运行差异、成本与错误类型；无真实模型权限时仅交付明确标注的离线演示和待验证项。

交付什么

  • 任务与评价规范、许可说明、数据划分标识、提示词和模型配置。
  • 逐次请求 / 响应或脱敏轨迹 .jsonl、工具执行记录、费用与耗时表、评测代码和失败样例。

怎样确认完成

  • 能回答“这条结果是哪次真实执行产生的”，并定位到数据、代码与模型配置。
  • RAG 引用能回到来源片段；Agent 的完成判断由实际任务状态或独立检查支持。
  • 基线与新方法的资源和评价口径已说明，人工样例与真实数据结果明确分开。
需要换工具或增加工具时
  • 小型 RAG 起步可先用简单检索与文件索引验证评价，再决定是否需要向量数据库。
  • AI 辅助工具可帮助解释和起草，但模型服务、GPU、Docker、框架与账号需要按任务另行准备和验证。

容易误用的地方

  • 有聊天软件或编辑器扩展，不等于有实验 API、GPU、模型权限或可公开的数据。
  • 不得把缓存回放、手工填写轨迹或模拟响应描述成实时模型实验；也不要将未授权材料发给外部服务。
科研训练任务卡 ↗实验、复现与运行证据 ↗AI 辅助使用与披露记录 ↗

功能依据 VS Code：Python 环境、调试与测试 · Python：独立虚拟环境与重建 · Git：记录变更与检查差异

05

论文撰写、规范检查与送审

让主稿、引文、图表、修改说明和最终送审版本保持一致。

返回选择 ↑

初学者最小组合Word + Zotero 引文插件 + Zotero + draw.io

按这几步推进

  1. 先下载本人适用的学校模板并选定主稿格式：Word 路线使用样式与引文插件；学校允许且已有基础时，选 LaTeX + VS Code 作为主稿。
  2. 按研究问题、方法、证据和局限组织章节；图表从真实结果生成，保存可编辑源文件，题注、单位、引用与正文一致。
  3. 每轮修改保留版本和问题回复表；Word 使用修订与批注协作，LaTeX 使用 Git 差异与编译日志，统一维护同一份主稿。
  4. 按学校要求检查格式、查重、非学术性差错与 AI 使用说明。匿名送审另存副本，检查封面、致谢、正文自引、文件名、属性、批注、修订、附件和链接。
  5. 从最终副本导出 PDF 并逐页检查字体、公式、分页、交叉引用和匿名性；登记送审文件版本、日期与提交回执。

交付什么

  • 主稿 .docx，或 .tex + .bib + 图表源文件；对应最终 .pdf。
  • 修改回复表、格式与匿名核对表、适用制度依据、允许保留的检测报告和提交回执。

怎样确认完成

  • PDF 与所登记主稿一一对应，图表与原始结果一致，所有引文都能定位。
  • Word 隐藏标记不代表删除修订；在送审副本中按要求处理修订与批注后重新检查。
  • Word for Mac 没有 Windows 的 Document Inspector；应核对属性并人工检查正文、批注、修订和导出 PDF，不能仅凭某个按钮宣称已完全匿名。
需要换工具或增加工具时
  • Word 和 LaTeX 二选一作为主稿；需要格式转换时以转换后的全文重新验收，避免同时维护两套正文。
  • Markdown 适合提纲和阅读笔记；转入学校 Word / LaTeX 模板后仍需完成排版核验。

容易误用的地方

  • 学校认可的检测系统与阈值以适用规定为准，不用通用 AI 或商业网站的分数替代。
  • 不要在唯一主稿上删除引文域、批注或身份信息；保留受控原稿与送审副本。
学位论文写作与版本检查 ↗学术规范、查非与查重 ↗送审准备与意见逐条回复 ↗

功能依据 Zotero：Word 插件与引用更新 · Zotero：书目与 BibTeX / RIS 导出 · Word：修订与隐藏标记的区别 · Word：文档检查与 Mac 版本差异 · LaTeX Workshop：编译工具链 · draw.io：源文件与 SVG / PDF 导出

06

竞赛协作、开题汇报与答辩

把团队分工、作品证据和现场表达连接起来，保证材料能交、演示能跑。

返回选择 ↑

初学者最小组合PowerPoint / Keynote + Git + draw.io

按这几步推进

  1. 建立任务清单，给每项任务写负责人、完成条件、检查日期与交付位置；竞赛先记录官方规则、版本和提交要求。
  2. 用 draw.io 梳理系统与方法，用 PowerPoint 或 Keynote 组织“问题—方案—证据—贡献—局限”；每张结果页标明证据来源。
  3. 按当前代码版本准备真实演示输入、关键操作和失败预案；记录团队贡献、素材来源与必要的权属约定。
  4. 按正式时长彩排，使用实际设备测试字体、投屏、音视频和网络依赖；另存 PDF、可脱网演示材料和问题回应清单。
  5. 提交前核对文件格式、大小、命名与版本；保存回执，赛后或答辩后把修改意见转成行动项。

交付什么

  • .pptx 或 .key 主文件、备用 .pdf、演示脚本、作品版本和合法可分享的演示视频。
  • 任务分工表、问答清单、修改记录、贡献说明与正式提交回执。

怎样确认完成

  • 在另一台目标设备试放，关键步骤不依赖临时登录或未知权限。
  • 陈述能区分个人贡献、团队贡献和复用内容；作品成果与现场展示一致。
  • 断网或服务失效时能说明哪些功能未现场验证，备用视频标明为录制材料。
需要换工具或增加工具时
  • 熟悉 Keynote 可继续使用；接收方要求 PPTX 时提前导出并逐页试放。
  • 远程讨论可用腾讯会议；Boardmix / EdrawMind 适合头脑风暴，定稿结论要落入可交付文档与任务记录。

容易误用的地方

  • 漂亮幻灯片和演示视频不能代替可运行作品或实际实验。
  • 竞赛报名成功、内部彩排通过与学校正式开题或答辩通过是不同状态。
竞赛立项、备赛与复盘 ↗答辩准备与修改验收 ↗会议、讨论与决策记录 ↗

功能依据 draw.io：源文件与 SVG / PDF 导出 · Git：记录变更与检查差异

07

日常管理、数据归档与交接

让工作能追踪、资料能找到、结果能复查，交接后仍可继续使用。

返回选择 ↑

初学者最小组合VS Code + Git + Excel

按这几步推进

  1. 用一个固定任务表维护目标、负责人、状态、日期和证据链接；周报与会议纪要沿用模板，重要决定由相关人员确认。
  2. 代码和文本放版本库；原始数据、模型、文稿原件与敏感材料按权限放受控存储，区分原始资料、处理产物和正式发布版本。
  3. 归档时写目录说明、数据字典、来源许可、环境与运行步骤，记录版本、文件清单和必要校验值；链接要指向接收方有权访问的位置。
  4. 另设备份位置或单位认可的备份服务并检查恢复；交接时由接收者实际打开材料、重跑最小样例、确认权限和待办事项。

交付什么

  • weekly.md、meeting.md 或对应 Word 记录；任务表与阶段证据索引。
  • README.md、文件清单、数据字典、校验清单、受控备份记录和交接确认。

怎样确认完成

  • 随机抽一个结论能追溯到原始资料、处理脚本和当前输出；无效链接已修复。
  • 备份能恢复，接收者实际拥有所需访问权限；通过组织授权的权限转移或账号移交程序办理，不共享个人账号密码。
  • 公开材料无个人信息、账号、密钥和未授权数据；受限资料保留必要来源与权限说明。
需要换工具或增加工具时
  • 日常笔记可用 Obsidian / OneNote，简单计划可用 Excel；已有团队平台时继续沿用，避免重复维护多个状态表。
  • EdrawProj 可辅助较复杂的进度安排；只有跨团队依赖较多时再增加工具，正式审批仍走学校指定渠道。

容易误用的地方

  • Git 提交、网盘同步和完整备份是不同工作；删除也可能同步到远端，应验证恢复路径。
  • Git LFS 存放大文件指针与外部内容，仍需考虑服务配额、访问权限与备份；不是无条件的数据保险箱。
